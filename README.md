# Codex Prompt Engineering

把需求、讨论和 Bug 报告整理成可直接交给编码代理的任务提示词，保留关键事实、最新决定、修改范围和验收条件。

适合复杂需求整理和跨任务交接。根据任务选择短指令、结构化任务书或发现任务书，避免把简单修改写成冗长规格。核心规则见 [SKILL.md](SKILL.md)。

## 快速开始

### 1. 安装到 Codex

如果你的 Codex 环境提供 `$skill-installer`，可以直接发送以下请求；已经安装的用户可跳到下一步。

```text
使用 $skill-installer 从以下 GitHub 仓库安装 codex-prompt-engineering：
https://github.com/SongJiaGang-del/codex-prompt-engineering
SKILL.md 位于仓库根目录，安装名称使用 codex-prompt-engineering。
```

本仓库提供 Codex 的 skill 规则与界面元数据。生成的提示词也可交给 Cline 或其他编码代理；其他工具的原生 skill 加载方式和兼容性未在本仓库验证。

### 2. 提供需求并调用

下面是一个可复制的虚构示例：

```text
使用 $codex-prompt-engineering，把下面的需求整理成可交给下一位代理的任务提示词：

资料页保存后偶尔仍显示旧值，刷新后恢复。我猜与缓存有关，但尚未收集日志。
先诊断，有证据后再做最小前端修复；不修改后端，不增加依赖。
相关文件和测试命令尚不清楚，要求接手代理先检查仓库。
本次只生成提示词，不执行诊断或修改。
```

也可以整理当前对话：

```text
使用 $codex-prompt-engineering，将以上讨论整理成下一轮执行提示词。
保留最新明确决定、已批准范围、禁止事项和验收要求；标明尚未解决的问题。
```

### 3. 核对后交接

输出会优先给出可直接使用的提示词。核对其中的事实、范围和待确认事项后，再交给执行代理；执行时仍需按实际仓库、工具和环境验证。

## 什么时候使用

| 你的请求 | 是否适合 |
| --- | --- |
| “把这段需求整理成实现提示词” | 适合：明确目标、范围、接口和验收 |
| “将长讨论交给另一个任务继续做” | 适合：保留有效决定和关键上下文 |
| “把 Bug 报告整理成诊断与修复任务” | 适合：区分已知现象与根因假设 |
| “为一次重构或审查写任务规格” | 适合：明确保留行为、审查范围和结果要求 |
| “现在直接帮我修 Bug、写代码或设计页面” | 使用对应的诊断、实施或设计工作流 |

已有清晰规格的简单任务通常可以直接执行，无需先经过一次提示词整理。本 skill 不接管普通代码实现、调试、安全审查、测试、UI 设计、调研或文档工作。

## 输出如何随任务调整

| 形式 | 适用情况 | 输出重点 |
| --- | --- | --- |
| 短指令 | 范围明确、风险低的小修改 | 一段文字或少量条目：目标、限制、适量验证 |
| 结构化任务书 | 多行为、接口或验收约束需要协调 | 上下文、当前决定、范围、契约、实施要求和验收 |
| 发现任务书 | 根因、目标或关键契约尚未确定 | 检查什么、需要哪些证据、哪些实施工作依赖结论 |

只保留有用章节；已有规格足够时，优先提取当前任务或定向修改。更多写法见 [三个完整示例](references/examples.md)。

简单任务可以短到下面这样。素材来自 [行为抽查案例 A](evals/README.md)，路径为虚构输入：

```text
在 src/pages/Login.vue 中，将登录表单提交按钮的文案从“确定”改为“登录”。
仅修改这一处文案，不改样式、点击行为或其他文件。完成后只检查 diff 并报告结果；不要启动浏览器或增加测试。
```

## 整理时会保留什么

- **事实与来源：** 区分用户要求、已核实事实、转述或假设、可选建议。关键事实保留来源及适用范围；未知路径、接口、依赖和命令要求先发现。
- **当前决定：** 后续明确修订取代旧决定，已撤销方案不再作为实施要求；局部修改不取消其他限制，未解决冲突仍需说明。
- **实施边界：** 保留允许修改的范围、禁止事项和授权边界。疑似根因不能变成指定修复，但授权范围内的可逆诊断试验仍可用于检验假设。
- **验收条件：** 区分计划验证、已验证和未验证／受阻事项。源码、构建、测试、浏览器交互及人工验收各自只证明其覆盖范围。
- **关键要求：** 输出前对照原始材料检查遗漏与新增要求，删除重复背景；默认不再额外输出一份检查表。

提供需求时，尽量带上期望行为、允许和禁止的改动、已知文件或契约、复现证据、验收方式，以及被后续修订的决定。不知道的内容直接注明未知，无需先填满模板。

## 验证情况与限制

2026-09-13 已完成结构与链接检查，以及三个虚构案例的提示词行为抽查，共保留四份生成输出：

- 简单修改和讨论修订两个案例各运行一次，观察到关键范围和验收条件得到保留。
- 根因不明的 Bug 案例首轮出现对诊断试验的过度限制；定向修改后，由新的独立代理复测该案例，未再观察到同一限制。
- 前两个案例没有在最终候选版本重新运行。记录保留了各自被测版本，没有将其合并宣称为最终版本全量回归通过。

查看 [抽查方法](evals/README.md) 和 [完整输出与复测记录](evals/2026-09-13-results.md)。

这是指令型 skill，没有额外执行工具。本次未在真实项目中对照“直接执行”“通用模板”和“使用本 skill”的结果，因此尚无编码成功率、Token 节省或总耗时改善的证据。提示词生成完成，也不代表其中描述的实现已经完成或通过验收。
